# Telegram News Aggregator

## Большие статьи: «По документам»

Проверенные авторские материалы находятся в `content/longreads/`. В `queue.json`
указываются уникальный `slug`, пути статьи и анонса, `publish_at` с часовым поясом,
`approved: true`. Отдельная автоматизация в основном чате готовит новые темы по средам
и воскресеньям. Сам GitHub workflow не сочиняет расследования и не проверяет источники:
он публикует только уже подготовленную одобренную очередь.

`python -m scripts.publish_longread` — безопасный preview; `--live` разрешает Telegraph
и один анонс в `@GVOZDIchKAAA`. `--immediate` действует только для записи с явно
заданным `publish_immediately: true` (первый MAX по прямому запросу владельца).
В обычной очереди этот флаг должен быть `false`. Буча стоит на 21.10.2026, 18:00 МСК.

Публикатор запускается перед обычными новостями. Учитывает общий лимит десять постов
по Москве и паузу минимум час; отправляет максимум один материал за запуск.
Плановое время — самое раннее допустимое, не гарантия точной минуты: GitHub может
задержать запуск, а пауза после предыдущего поста переносит отправку. Обычные статьи
не выходят ночью и не догоняются позднее чем через двое суток. Push контента запускает
проверку очереди, но сам по себе не разрешает досрочную отправку.

Итоговый URL Telegraph и ID Telegram записываются в общий state, который защищён той
же группой concurrency, что и обычная лента. Учётная запись Telegraph сохраняется
там только в шифротексте Fernet; ключ выводится из секретного токена бота. В логи
токен не попадает. При смене токена бота нужна отдельная безопасная миграция доступа
Telegraph с прежним ключом; автоматическое создание новой учётной записи запрещено.
Поэтому не удаляйте шифротекст при ротации и сохраняйте прежний секрет безопасно до
миграции; не публикуйте его в чат, репозиторий или артефакты Actions.

После неопределённого ответа внешнего сервиса запись `page_creating`/`sending`
останавливает повторную отправку только данной статьи. Нужна ручная сверка на
Telegraph/в канале; нельзя просто сбросить статус и повторить команду. Ошибка статьи
не блокирует обычные новости. Все изменения state, включая намерение отправки,
сохраняются и при ошибке публикатора. Проверка фактов и прав на изображения остаётся
обязанностью редакционного процесса, а не тестов издателя.

Автоматизированный русскоязычный канал жёсткой авторской сатиры
[`@GVOZDIchKAAA`](https://t.me/GVOZDIchKAAA). Он получает материалы из RSS, отбирает
темы канала, удаляет дубли, извлекает текст статьи, определяет редакционный режим,
создаёт оригинальный короткий пост, проверяет сохранность фактов и отправляет результат
на review. Публикация в публичный канал по умолчанию **выключена**.

Это не RSS-репостер и не fact-checker. Исходная публикация используется как источник
фактов, длинные фрагменты не копируются, а атрибуция и степень уверенности должны
сохраняться.

## Pipeline

```text
RSS → topic/emergency filter → URL/title dedupe → article extraction → mode classifier
    → editorial context → LLM or fallback rewrite → fact-preservation validator
    → review/publish → SQLite
```

1. `FeedCollector` читает только явно настроенные RSS/Atom feeds.
2. `TopicFilter` анализирует заголовок, описание и RSS-категории. Публикация должна быть
   напрямую связана с Россией; зарубежные новости без такой связи, спорт, lifestyle и
   развлекательные материалы отсекаются правилами.
3. `Deduplicator` сравнивает canonical/normalized URL, нормализованный заголовок,
   token-set similarity и эвристику одинакового именованного события.
4. `ArticleFetcher` берёт canonical URL и абзацы из `article`/`main`; при недоступности
   страницы использует RSS description или метаописание.
5. `editorial_mode` по умолчанию выбирает `SATIRICAL` для безопасных тем, а не ждёт
   редкого ключевого слова «абсурд». Жертвы, медицинские риски, боевые действия,
   катастрофы и репрессии сохраняют `HARD_NEWS`. Чиновничья карьера или расследование
   коррупции допускают сатиру в адрес публичного лица, но не выдуманную виновность.
6. Rewriter создаёт самостоятельный авторский мини-текст: сатирический заход,
   конкретные факты и едкую человеческую концовку. Не просто новость с приклеенной шуткой,
   не канцелярит и не повторение лозунгов. Мишень — публичное решение, бюрократия,
   самооправдание и пропаганда, не частные люди или национальность. Эмодзи чередуются.
7. Validator отклоняет новые/изменённые числа, даты, суммы, проценты, имена и организации.
   Это защита от ошибок переписывания, а не проверка истинности исходника.
8. Редакционный слой ставит уровень подтверждения, находит предыдущий пост по теме,
   распознаёт исправления и сопоставляет обещания с последующим результатом.
9. В `REVIEW_MODE=true` пост идёт в review-чат либо только в log. Только явное
   `REVIEW_MODE=false` разрешает отправку в `TELEGRAM_CHANNEL`.

Архитектура разделяет сбор, фильтрацию, дедупликацию, rewrite и validation. Позже можно
добавить fact checking, provenance, поиск первоисточника, проверку медиа и сопоставление
нескольких источников без переписывания transport/storage слоя.

## Установка и локальный запуск

Нужен Python 3.11+ (workflow использует 3.12).

```bash
python -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate
python -m pip install -r requirements.txt
cp .env.example .env             # Windows: copy .env.example .env
python main.py --dry-run
```

Локальный dry-run никогда не вызывает Telegram. Он готовит до пяти пригодных публикаций
и до трёх спорных previews; лимит пригодных меняется через `--max-items 10` или
`MAX_ITEMS_PER_RUN`.
Ключ `--digest` (или `DIGEST_MODE=true`) объединяет выбранные материалы в один утренний
или вечерний пост. `--emergency-only` берёт только свежие чрезвычайные события последних
трёх часов, а `--weekly-digest` собирает пять наиболее значимых и неповторяющихся тем за
семь дней. `--quote-of-day` ищет атрибутированную прямую цитату и не публикует вторую
цитату в тот же московский день. `--process-editor-messages` обрабатывает только
личные команды редактора без сбора новостей.
`--scheduled-release` выпускает не более одного поста за запуск в текущем дневном слоте,
с паузой не меньше часа после последней реальной публикации. Пропущенные слоты не
накапливаются и не догоняются пачкой; повторный запуск в заполненном слоте не даёт поста.

Тесты:

```bash
python -m pytest
```

## Rewrite: LLM и fallback

Abstraction находится в `rewriter/base.py`, реализации — в `rewriter/llm.py` и
`rewriter/fallback.py`.

Если `LLM_API_KEY` задан, используется OpenAI-compatible Chat Completions endpoint:

```dotenv
LLM_PROVIDER=openai
LLM_API_KEY=...
LLM_MODEL=gpt-4.1-mini
# Для совместимого провайдера:
# LLM_PROVIDER=openai_compatible
# LLM_BASE_URL=https://provider.example/v1
```

Если ключа нет или провайдер временно отвечает ошибкой, запуск не падает: fallback
очищает RSS description, сокращает его и оформляет короткий пост с источником. Fallback
не придумывает аналитический контекст.

## Validation и статусы

Материал может получить, среди прочего, статусы:

- `FILTERED_OUT` — не прошёл тему;
- `NOT_EMERGENCY` — прошёл обычный фильтр, но не подходит для экстренного выпуска;
- `VALIDATION_FAILED` — rewrite добавил/изменил проверяемый факт;
- `DRY_RUN` — preview создан локально;
- `REVIEW_READY` — preview выведен в log, review-чат не настроен;
- `SENT_TO_REVIEW` — отправлен редактору;
- `REVIEW_PENDING` — спорный материал удержан в очереди до личного решения;
- `REJECTED` — редактор отклонил материал;
- `PUBLISHED` — опубликован при явно выключенном review mode;
- `SEND_FAILED` / `CONFIGURATION_ERROR` — Telegram или конфигурация требуют внимания.

`VALIDATION_FAILED` никогда не публикуется. В SQLite сохраняются URL, canonical и
normalized URL, заголовок, источник, даты публикации/обнаружения, статус, hash текста,
режим, темы и Telegram `message_id`.

## Telegram setup

1. Создайте бота через `@BotFather`.
2. Откройте личный чат с ботом и отправьте `/id`. При следующем рабочем запуске бот
   ответит числовым ID. Для очереди спорных материалов сохраните его в `EDITOR_CHAT_ID`.
   Группа не нужна.
3. Для будущей публикации добавьте бота администратором канала с правом публикации.
4. Никогда не коммитьте токен или `.env`.

Локальные переменные:

```dotenv
TELEGRAM_BOT_TOKEN=...
TELEGRAM_CHANNEL=@GVOZDIchKAAA
REVIEW_CHAT_ID=
EDITOR_CHAT_ID=123456789
REVIEW_UNCERTAIN=true
REVIEW_MODE=true
```

При `REVIEW_MODE=true`:

- с `REVIEW_CHAT_ID` preview отправляется только туда;
- без `REVIEW_CHAT_ID` preview остаётся только в log;
- workflow безопасно проверяет, что бот является администратором канала и имеет право
  публиковать сообщения, не отправляя тестовый пост;
- публичный канал не используется.

При автопубликации цель — **10 отдельных сообщений в сутки**, а не только верхний
предел и не десять новостей внутри нескольких дайджестов. Суточный учёт ведётся по
московскому дню. Счётчик учитывает уникальные Telegram message ID: один дайджест с
двумя историями считается одним постом. Плановые выпуски теперь одиночные;
объединённый дайджест остаётся доступен вручную.

Время планируется **по Москве**: десять дневных слотов в окне 08:00–20:00,
с небольшим разбросом вокруг среднего интервала 72 минуты. Плановые интервалы
составляют 46–98 минут. Время меняется каждый день, но одинаково для всех повторных
запусков в тот же день: дневной seed не зависит от случайного состояния процесса.
Это позволяет разнообразить ритм, не менять план при перезапуске и не создавать дубли.

Конкретные десять времён текущего дня печатаются в журнале как «Плановые времена
по Москве». Это время готовности очередного слота, а не обещание запуска с точностью
до минуты: проверки идут каждые полчаса, а GitHub может дополнительно задержать их.
В Сан-Франциско эти времена на 10 часов раньше при PDT и на 11 часов раньше при PST;
для первых московских слотов календарная дата там может быть предыдущей.

Workflow проверяет план каждые полчаса, в `:17` и `:47` по UTC. После задержки выходит
максимум одна обычная публикация для текущего слота, а не весь недостающий объём.
Между обычными автоматическими выпусками — минимум 60 минут; один фактический пост
заполняет текущий слот. С 20:00 до первого следующего дневного слота обычные посты не
выходят; долги предыдущего дня не переносятся. В заполненном слоте, во время паузы
или ночью проверяются только срочные новости.
Срочное событие не ждёт случайного дневного слота: при ближайшей проверке оно получает
приоритет и рубрику «СРОЧНО», в том числе во время обычного выпуска. Экстренные
посты, цитата дня и итог недели входят в десять, не добавляются сверх них.

По воскресеньям в 21:32 по Москве (11:32 PDT / 10:32 PST в Сан-Франциско) выходит
«Итог недели» со ссылками на пять ключевых постов; резервируется одно место. Если
этот запуск пропущен, ближайшая плановая проверка также пытается выпустить итог.
В 14:32 по Москве (04:32 PDT / 03:32 PST в Сан-Франциско) отдельно проверяется
«Цитата дня». При отсутствии цитаты её место заполняется обычной новостью.
Цитата и итог недели также ждут окончания часовой паузы после последнего поста.
Срочная новость может выйти раньше часа, но по-прежнему учитывается в дневном лимите.

Количество не отменяет фильтры: только новости, связанные с Россией, без дублей,
искажённых фактов и неподтверждённых утверждений. После трёх спорных кандидатов
отбор продолжается; они больше не обрывают весь выпуск. За запуск проверяется до
40 кандидатов, в очередь личной проверки добавляются максимум три новых карточки.
При нехватке пригодных материалов недобор записывается в журнал и, если подключён
`EDITOR_CHAT_ID`, сообщается редактору. GitHub может задержать или пропустить запуск;
без работающего планировщика или достаточного числа новостей абсолютная гарантия
десяти постов невозможна. [Ограничения расписания GitHub](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule).
Лимиты настраиваются переменными `MAX_ITEMS_PER_RUN`, `DAILY_POST_LIMIT` и
`POST_TIMEZONE`. Внизу поста показывается только кликабельное имя источника: сырой URL
скрыт, но Telegram по-прежнему строит карточку материала с медиа. Превью явно привязано
к исходной статье, поэтому ссылка «Ранее» не заменяет картинку карточкой старого поста.

Похожие заголовки из разных RSS используются как сигнал дополнительного подтверждения.
Одиночные посты и материалы дайджеста получают пометку: `🟢 О событии сообщают несколько
изданий`, `🟡 Пока один источник`, `🔴 Заявление стороны`, общий первоисточник либо
расхождение данных. Система распознаёт явную атрибуцию к ТАСС, РИА Новости, Минобороны и
другим настроенным первоисточникам; повторное заявление не становится установленным
фактом из-за количества пересказов. Разные числа или опровержение в похожих заголовках
отправляют материал на проверку. Истинность и независимость сообщений автоматически
не гарантируются.

Если новая публикация содержит явный сигнал новых данных по уже известному сюжету, она
выходит с отметкой `ОБНОВЛЕНО` и, когда сохранён Telegram `message_id`, со ссылкой
«Ранее». Явные опровержения и уточнения получают рубрику `ИСПРАВЛЕНИЕ`. Если новый
материал сообщает о срыве, переносе или результате прежнего обещания, агрегатор пытается
найти связанный старый пост и оформить `Обещали / получилось`. В пост добавляется
короткое точное прежнее обещание или заголовок с датой выпуска. Учитываются и неудачи,
и успешный запуск. Эти связи эвристические и строятся только по сохранённым публикациям.

Авторская подача — свободная и критическая, но масштаб события не раздувается.
Предпочтение отдаётся значимым событиям: решениям властей, коррупции, давлению на людей,
сбоям инфраструктуры и угрозам общественной безопасности. Для содержательной критики
используется схема «что произошло → где система дала сбой → последствия для людей».
Причины, ответственные и последствия берутся из источника; неизвестная причина так
и называется неизвестной. Локальный случай не превращается автоматически в угрозу
всей стране. Медицинские прогнозы не выдумываются. Новости о санитарных рисках и
пострадавших подаются серьёзно; колкость адресуется управленческому решению, не жертвам.

Отбор учитывает значимость самого события, свежесть, повторы недавно освещённого сюжета
и разнообразие подачи. Материалы старше `NEWS_MAX_AGE_HOURS=48` по умолчанию не берутся
в обычные выпуски. Недельный итог содержит пять разных событий и вывод о теме подборки,
основанный на её составе, без универсальных утверждений об итогах всей страны.

`EDITORIAL_STYLE=satirical` — основной стиль обычных публикаций, цитаты дня и
сопоставления обещаний с результатом. Сатира проходит через текст, не заменяя детали:
названия, даты, суммы, источник обвинения и степень уверенности сохраняются.
В `SATIRICAL` дополнительно включён максимально едкий, почти памфлетный профиль:
короткие фразы, сатирический напор, пародия на канцелярит, чёрный юмор в адрес публичных
решений и беспощадная последняя фраза. После концовки не объясняется шутка и не
добавляется примирительная мораль. Тот же профиль действует в ремарках новых рубрик.
Чернота юмора не означает использование смерти, болезни или страдания как реквизита,
вымышленных ответов чиновников, пожеланий вреда или призывов к насилию. Ругательство
допустимо редко как авторская оценка решения, но не обязательно и не заменяет мысль.
Этот профиль не передаётся автору в `HARD_NEWS`/`ANALYSIS`; проверки фактов и существующая
редакторская проверка оскорбительных формулировок не ослаблены. Нового отдельного
LLM-редактора, увеличения температуры, числа попыток или суточного лимита нет.
В структурированных авторских карточках расчёты и доказательные фрагменты не
переписываются: отдельно добавляется краткая концовка из уже проверенного LLM-текста,
без новых чисел, дат или цитат. Если подходящей концовки нет, карточка остаётся фактической.
Проверки — формальные эвристики, не гарантия смысловой достоверности или удачной шутки.
Экстренные выпуски, исправления, трагедии и репрессии подаются серьёзно. Контрольные
напоминания без новых сведений и недельная подборка ссылок остаются фактологическими.
При сбое LLM используется исходный пересказ без искусственно придуманной шутки.
Для возврата к прежнему выбору тона по событию задайте `EDITORIAL_STYLE=news`.

## GitHub Secrets, Variables и Actions

В **Settings → Secrets and variables → Actions** добавьте secrets:

- `TELEGRAM_BOT_TOKEN` — основной токен Bot API;
- `TNEWS_AGGREGATOR_BOT` — резервное имя для ранее созданного secret;
- `REVIEW_CHAT_ID` — приватный review-чат;
- `EDITOR_CHAT_ID` — положительный числовой ID личного чата редактора;
- `LLM_API_KEY` — необязательно, fallback работает без него.

Repository variables:

- `REVIEW_MODE=true` — обязательный безопасный старт;
- `TELEGRAM_CHANNEL=@GVOZDIchKAAA`;
- `LLM_PROVIDER=openai` — необязательно;
- `LLM_MODEL=gpt-4.1-mini` — необязательно;
- `LLM_BASE_URL` — только для совместимого endpoint.
- `NEWS_MAX_AGE_HOURS=48` — максимальный возраст обычной новости;
- `EDITORIAL_STYLE=satirical` — авторская сатира по умолчанию; `news` — прежний режим;
- `SATIRE_RUBRICS=true` — три дополнительные сатирические рубрики (до двух сообщений в неделю);
- `STYLE_VARIATION=true` — память стиля и одна попытка переписать повторившуюся шутку;
- `REVIEW_UNCERTAIN=true` — удерживать спорные материалы до проверки.

Workflow `.github/workflows/aggregator.yml` запускает плановые одиночные выпуски, экстренные
проверки, проверку цитаты, воскресный итог и доступен вручную. `concurrency` не допускает
параллельной публикации. Каждый запуск сначала выполняет unit tests.

Для ручного запуска откройте **Actions → News aggregator → Run workflow**. Опция
`dry_run` по умолчанию включена; такой запуск проверяет доступ бота только чтением,
не отправляет сообщения и не меняет постоянное состояние. Он работает на временной
копии сохранённой базы, поэтому учитывает реальную историю. Поле `run_mode` позволяет
выбрать `scheduled` (тот же режим, что `auto`), `news`, `digest`, `quote`, `emergency`,
`weekly` или `editor` для проверки отдельной функции. `news` — один ручной выпуск;
`auto` / `scheduled` — максимум один пост для текущего слота, даже при `--max-items 10`.

### Личная проверка спорных материалов

Сомнительные сведения, расхождения между лентами, потеря ключевых деталей, ошибки
переписывания и оскорбительные ремарки удерживаются в `review_queue`. Если модель
исказила проверяемые факты, на проверку поступает проверенный fallback-пересказ.
Не прошедший повторную validation материал не допускается к публикации.

При заданном `EDITOR_CHAT_ID` бот присылает до трёх новых карточек за проверку, с причиной
и командами `/publish N` и `/skip N`. Команды принимаются только из этого личного чата
от того же пользователя. Без ID очередь сохраняется, обычные пригодные новости выходят
как раньше. Одобрение учитывает дневной лимит, запрет повторной цитаты и возраст карточки
не более 48 часов. Повторная команда не публикует обработанную карточку ещё раз.
Команды разбираются при каждом рабочем запуске; для немедленной обработки выберите
`run_mode=editor`, `dry_run=false`. `/id` сообщает пользователю только его собственный
ID и не назначает его редактором автоматически. `/start` открывает инструкции для
предложений читателей, а редактор с настроенным ID может посмотреть `/requests`.

Используемые методы и настройки карточек описаны в
[Telegram Bot API](https://core.telegram.org/bots/api#linkpreviewoptions).

### Persistence

Runner GitHub Actions эфемерен, поэтому cache не используется как источник истины.
После успешного не-dry запуска workflow сохраняет `data/state.db` единственным commit в
отдельную ветку `state`; перед следующим запуском база восстанавливается оттуда.
Служебная ветка перезаписывается только этим workflow. Для этого job имеет минимально
необходимое разрешение `contents: write`. В основной ветке `*.db` игнорируются.

Если организация запрещает запись `GITHUB_TOKEN`, включите **Settings → Actions →
General → Workflow permissions → Read and write permissions**.

## Переход к autopublish

Не меняйте код. После проверки previews:

1. убедитесь, что бот — администратор `@GVOZDIchKAAA`;
2. проверьте `TELEGRAM_BOT_TOKEN` (либо резервный `TNEWS_AGGREGATOR_BOT`) и `TELEGRAM_CHANNEL`;
3. оставьте review включённым ещё на несколько плановых запусков;
4. измените repository variable `REVIEW_MODE` с `true` на `false`;
5. вручную запустите workflow с `dry_run=false` и проверьте одну публикацию;
6. чтобы немедленно вернуться в review, снова поставьте `REVIEW_MODE=true`.

## Security

- `.env`, базы, журналы SQLite, venv и IDE-файлы исключены из Git.
- Токен не печатается в logs; ошибки Telegram логируются только по типу.
- Автопубликация требует явного переключателя.
- Код не читает приватные Telegram-аккаунты и не делает массовых рассылок.
- Fact checking, OSINT, image/video verification, face recognition, tracking и political
  ad targeting намеренно не реализованы.

## Ограничения MVP

- Rule-based topic/mode classification требует периодической настройки словарей.
- Fuzzy dedupe распознаёт очевидные совпадения и однотипные именованные события, но не
  заменяет semantic clustering.
- Validator проверяет сохранность формальных сущностей, а не истинность заявления.
- Fallback обычно ближе к сжатому пересказу RSS; полноценный оригинальный редакционный
  текст и контекст лучше получать через LLM с обязательной post-validation.

## Авторская редакция: пять новых рубрик

Включены по умолчанию (`AUTHOR_FEATURES=true`). В плановом выпуске — **не более одной**
новой авторской рубрики за московские сутки, **внутри**, а не сверх общего лимита 10
сообщений. Если доказательств недостаточно, выходит обычная пригодная новость; рубрика
не создаётся ради количества. Срочные новости и исправления не подменяются рубрикой.
«Тихая правка» и мониторинг редактирования сайтов не добавлены.

1. **Кто отвечал.** Из текущей статьи извлекаются прямо названные роли/решение и ещё
   хотя бы один блок: деньги или результат. Сохраняются атрибуция и степень уверенности.
   Назначение заказчиком/подрядчиком не объявляется доказательством уголовной вины.
   Это карточка по доступному источнику, не самостоятельное расследование закупок.
2. **Не забыли.** Опубликованные истории о выплатах, обещаниях, ремонте, расследованиях
   и других значимых процессах ставятся на проверки через 7 и 30 дней. Начальный
   заголовок, дата выпуска и ссылка на него сохраняются отдельно, поэтому новое
   содержание статьи не переписывает исходную историю. Ищутся связанные свежие
   сообщения в подключённых RSS за последние 48 часов. При найденном продолжении
   показываются новая информация и оба источника, с превью нового материала.
   Если обновления нет, проверка проходит тихо: никаких постов «новых сведений нет»
   или «прошло N дней», никаких занятых слотов и авторской квоты. Пустой сбор тоже
   не создаёт поста. Уже освещённая статья, прежний заголовок, отсутствующие детали
   и текст без новых относительно сохранённого исходника сведений не дают продолжения.
   Проверка не продвигается после неудачной отправки. Запаздывание GitHub возможно.
3. **Две России в один день.** Сопоставляются заявление и сообщение о проблеме,
   опубликованные в один московский календарный день, с общим именованным объектом
   (например, сервисом или школой №7 в одном городе), темой и совместимым периодом.
   Просто две новости из одного города не образуют пару. Сохраняются оба источника;
   сопоставление само по себе не устанавливает причинность или сознательную ложь.
   Материалы другого дня, несовпадающих годов/месяцев и неидентифицируемых объектов
   автоматически не сопоставляются.
4. **Цена решения.** Поддерживаются явные изменения «с X до Y рублей» (включая
   тысячи/миллионы/миллиарды) и «с X до Y минут». Разница и процент вычисляются
   `Decimal`, формула выводится в посте. Годовой эффект считается только при прямо
   указанной ежемесячной сумме и помечается как условие её сохранения 12 месяцев.
   Нет выдуманной базовой цены, среднего дохода, числа членов семьи или пересчёта валют.
   Противоречивые/неопределённые данные и отсутствующая база не дают расчёта.
   При ручном одобрении суммы заново вычисляются; обычный validator не обходится
   произвольным разрешением новых чисел.
5. **Разбор по запросу.** В личном чате с `@tnews_aggregator_bot` читатель отправляет
   `/suggest HTTPS-ссылка`; необязательно после ссылки — `цена`, `ответственность`
   или `сравнение`. При достаточных данных бот строит соответствующий разбор,
   иначе — явно обозначенный пересказ того, что сообщает источник. Голос читателя
   учитывается один раз на ссылку, до 3 разных ссылок за 24 часа. Ссылка влияет на
   отбор только после независимого обнаружения в текущей подключённой RSS-ленте.
   Читатель не получает прав редактора, произвольный URL не скачивается, сообщение
   читателя не публикуется и не передаётся LLM. Группа не нужна.

### Приватность предложений

В базе **нет Telegram ID, имени, username или свободного текста** читателя. Сохраняются
только HMAC-отпечатки отправителя и нормализованной ссылки, категория запроса, имя
публичного источника и дата. Ключом служит секретный токен бота; он в базу не записывается.
Параметры URL и fragment исключаются. Сам URL сохраняется открыто лишь после его
независимого появления в публичном RSS. Это важно, потому что ветка `state` может быть
публичной. Новых секретов или настроек для запуска не требуется.

`/forget` удаляет текущий учёт запросов отправителя; не меняет публикации канала.
Очередь/учёт очищаются через 30 дней при рабочих запусках. Это удаление из текущей
базы, не обещание стирания исторических Git-снимков. После смены токена прежние
отпечатки не связываются с отправителем и перестают сопоставляться; старые записи
истекают по сроку. Telegram сам хранит чат: полной анонимности эта функция не обещает.
Очередь ограничена 200 материалами. Ответы читателям идут при очередном рабочем
запуске, не мгновенно; публикация и её сроки не гарантируются.

Ссылка «Предложить материал для разбора» появляется в авторских карточках и недельных
итогах, не в каждом обычном посте. Username задаётся `READER_BOT_USERNAME`.
Проверка отдельной рубрики без Telegram:

```powershell
python main.py --dry-run --state work/feature-preview.db --author-feature cost --max-items 1
```

Допустимые значения `--author-feature`: `auto`, `responsibility`, `followup`, `contrast`,
`cost`, `reader`, `translation`, `excuse`, `career`. Обычная новость остаётся резервным вариантом, если подходящей рубрики
нет. В Actions добавлен `run_mode=editorial`; его `dry_run` по умолчанию включён.

## Три сатирические рубрики и память стиля

`SATIRE_RUBRICS=true` добавляет три формата в обычный плановый выпуск. Общий бюджет
для них — **до двух сообщений за московскую неделю с понедельника**, не более одного
авторского формата за сутки и не сверх 10 сообщений. «Отмазка недели» выходит не
чаще одного раза за неделю. Отдельного дополнительного рассылочного таймера нет.
Рубрика выбирается из пригодного свежего материала; если доказательств или безопасной
ремарки нет, используется обычная новость. Читательский запрос, срочное сообщение,
исправление и сопоставление обещания с результатом не подменяются новой рубрикой.

- **Перевод с чиновничьего:** настоящая цитата, приписанная источником публичному
  должностному лицу/ведомству, с бюрократическим эвфемизмом. Цитата и её атрибуция
  сохраняются; ниже — отдельный **«Авторский перевод (сатира)»**. Это не новая цитата
  чиновника и не утверждение о его скрытых намерениях.
- **Отмазка недели:** реальное официальное объяснение и связанный с ним сбой в
  соседнем фрагменте той же статьи. Не сопоставляет произвольные проекты; не объявляет
  объяснение доказанной ложью или худшим во всей стране. Авторский разбор помечен как сатира.
- **Карьерный лифт:** источник прямо сообщает о прежнем провале/увольнении/высылке и
  новой должности либо работе одного человека. Требуется полное имя с совместимыми
  русскими окончаниями в обоих фрагментах, а не совпадение фамилии или неоднозначное
  «он». Даты сохраняются, если указаны; обратная хронология отсекается. Новая работа
  не объявляется повышением или наградой за провал без соответствующих сведений.

Жертвы, репрессии и трагедии не становятся сатирическими карточками. Фактологическая
основа собирается из точных исходных предложений; LLM пишет лишь одну ремарку
60–320 знаков. Новые числа, кавычки/цитаты и неподдерживаемые имена не допускаются.
Проверки остаются эвристиками, не полноценной проверкой смысла или достоверности источника.
Без LLM или при ошибке поставщика новые сатирические рубрики не имитируются заготовкой.

`STYLE_VARIATION=true` использует память последних **30 публично опубликованных**
сатирических текстов. Первоначальная память однократно заполняется недавними публичными
постами из базы. Заходы и концовки передаются тому же автору как образцы, которые
нельзя повторять, а не как новые факты. Дополнительно проверяются повторные фразы из
пяти слов, близкие заходы/концовки и узнаваемые заготовки. Дословная фактическая
формулировка из текущего источника не считается повтором шутки.

При повторе — **одна** попытка переписывания тем же автором, затем обычная проверка
фактов. Если повтор остаётся или запрос не удался, выходит исходный фактический
пересказ без повторившейся шутки. Для старой структурированной карточки повторная
добавочная концовка просто исключается. Новая рубрика без подходящей ремарки не выбирается.
Нет второго LLM-редактора, оценки каждой шутки отдельной моделью или безлимитных повторов.
Семантически похожие, но иначе сформулированные шутки могут пройти — это не гарантия
абсолютной оригинальности.

Память хранит только публичные тексты, сохраняется в существующей базе `state` и
переживает перезапуски. Черновики, приватный review, dry-run, отказанные и неотправленные
посты не попадают в неё. Новых токенов не требуется. Переключатели можно выключить
отдельно; ручное одобрение через существующий личный чат тоже соблюдает недельный бюджет.
